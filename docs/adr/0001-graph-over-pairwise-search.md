# ADR-0001. Веер поисков и проверенные стыковки через хабы

**Статус:** принято, 2026-08-19

## Контекст

MCP Туту отвечает на вопрос о конкретной паре городов. TravelBroke должен
ответить на обратный вопрос: «куда я могу уехать при таких ограничениях?» и не
терять выгодные составные варианты.

Полный перебор всех путей между тысячами городов не укладывается в лимиты MCP
и плохо объясняется пользователю: маршрут должен состоять из реальных,
пригодных к покупке офферов, а не из абстрактных весов рёбер.

## Решение

Расчёт идёт в две последовательные фазы.

1. `fan_out` опрашивает географически сбалансированный набор направлений и
   сохраняет конкретные варианты, цену и время по видам транспорта.
2. `deepen` берёт города без прямого оффера и дорогие направления, выбирает до
   трёх правдоподобных хабов на направление и ищет два реальных плеча через
   каждый хаб. Хаб не должен давать географический крюк более `1.35`.

Пара плеч становится одним маршрутом только после проверки расписания:
минимальный запас времени, максимум 20 часов ожидания и не более трёх
пересадок всего. В ответ уходят сами плечи и точки маршрута — фронтенд рисует
их на карте и строит deeplink для каждого билета отдельно.

`build_graph` и `cheapest_paths` остаются доменными помощниками и покрыты
тестами; они дают производное представление результата. Основной путь API не
подменяет конкретные офферы поиском абстрактного кратчайшего пути.

## Последствия

**Хорошее.** Пользователь видит именно тот составной маршрут, который
проверен по времени и может открыть на Туту. Веер остаётся полезным, даже если
ни одна стыковка не найдётся.

**Плохое.** Это эвристический, а не исчерпывающий поиск: за один расчёт не
проверяются все возможные хабы мира. Ограничения прозрачны и удерживают
задержку и число вызовов MCP в разумных пределах.

## Альтернативы

- Только прямой веер: быстрее, но не раскрывает ключевую механику продукта.
- Полный перебор всех путей: теоретически шире, но непрактичен для внешнего
  API и создаёт плохо проверяемые маршруты.
